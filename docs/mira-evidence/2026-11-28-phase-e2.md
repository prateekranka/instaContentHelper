## App behavior and storage

My Brand asks six questions, one at a time. It uses the existing voice permission and Settings behavior. Typing is available on each question. Mira returns topics, tone, audience, dos, don'ts and goals. Each item can be edited before “This is me” confirms the document.

Home makes one pick with a reason. “Show another idea” omits earlier titles. If a title exceeds the server limit for `avoid`, the app includes the full title in `recentIdeas`. “Make this one” opens Your words. Pictures use the accepted job's ID and the shot IDs for that job. Earlier batches still reopen. New three-card batches start at Profile → Plan step by step → Compare three ideas.

The latest confirmed brief on an unfinished, unarchived Reel supplies the active deal checklist. Using a pick rechecks the brief before it saves. An empty deal Reel can accept the pick directly. An existing plan keeps its work, and the pick creates a separate Reel using the reviewed brief.

The app adds two optional fields at the root of `mira-v2.json`. The document version stays at 2.

| Key | Saved value |
| --- | --- |
| `brandDoc` | The confirmed `pillars`, `tone`, `audience`, `dos`, `donts` and `goals`. |
| `instagramResultsPermission` | The creator ID and the Boolean choice for using Instagram results in E2 requests. |

Old files decode with both keys absent. Older builds ignore the new keys when reading. An older build that rewrites the file can drop the unknown keys. Pick jobs, their results and unfinished interviews stay in memory. The accepted Reel uses the existing idea, script, storyboard, navigation and picture-source fields. The existing AI permission store and record version are separate from the new Instagram choice.

## State machines

Every transition below uses the store and the machine's pure `handle` function. [State machine diagrams](../state-machines.md)

| Interview state | Events | Primary action |
| --- | --- | --- |
| `idle` | Start, reset | Start the interview |
| `answering` | Edit, back, next, generate, reset | Next or Make my brand doc |
| `generating` | Matched result, matched failure, account reset | Wait |
| `failed` | Generate again, back to answers, reset | Try again |

| Brand document state | Events | Primary action |
| --- | --- | --- |
| `empty` | Read saved value, receive a valid draft | Start the interview |
| `reviewing` | Edit draft, confirm valid draft, cancel to saved value | This is me |
| `confirmed` | Edit saved value, read from storage | Edit my brand doc |

| Pick state | Events | Primary action |
| --- | --- | --- |
| `idle` | Start, reset | Make today's Reel |
| `working` | Matched progress, result or failure, reset | Wait |
| `ready` | Start another, make, reset | Make this one |
| `failed` | Start again, reset | Try again |

## App request changes and source differences

- Before E2, the default Home request created three `todayIdea` jobs from the creator profile and filming constraints. E2 sends one `pickIdea` job with the confirmed brand doc, reviewed deal checklist and skipped titles when available. The `brandDoc` operation sends the interview answers and language. A separate Instagram choice gates any results included in those requests. The general consent version, device authentication, provider settings and deployed service are outside these changes. [Phase E server contract](2026-11-28-phase-e-server.md)
- The gap brief describes live best-post patterns. The current Instagram Insights source returns account metrics and a null `nudge`. It returns no per-post results. With permission, the client can pass the available follower count to `brandDoc` and a valid API-sourced pattern to `pickIdea` if one is available. The sample fixture supplies a pattern. Live pick requests with the current source omit it. [Instagram Insights implementation](../../supabase/functions/instagram-insights/index.ts)
- The shared build instructions name different rule counts. This checkout has eight rule groups. The Phase E server contract omits `conflicts` for a successful `brandDoc`, which the app decodes as an empty array.

## Reproduction setup

TesterArmy 0.15.2 uses iPhone 16 Pro “Bobby’s” and bundle `com.prateekranka.creatorcontenthelper`. The retained runner is `work/keep/run-e2-phone.sh`. It reads `work/keep/pr37-phone-3.env`, waits up to 15 minutes for existing phone claims, and runs under `caffeinate`. It does not install or remove an app. The Keep config reads AI permission and checks the Instagram handle after a normal launch.

After the passcode gate clears, run the gates in this order.

1. Run Keep with `nohup bash work/keep/run-e2-phone.sh keep-before`. Stop if Instagram or AI permission differs.
2. Install the signed device build over the installed app. Run the `keep-after-install` gate. Stop if either account check differs.
3. Start `tests/fixtures/mira-d2-server.mjs`. Set `MIRA_E2E_D2_ENDPOINT` to its phone-reachable HTTPS origin and `MIRA_D2_FIXTURE_CONTROL` to the control origin. Set a unique `MIRA_E2E_FIXTURE_SESSION` for the sample suite. Run the `run-1` gate.
4. Run the `live` gate once. It selects only `^E2 live ` from `e2e.mira-live-journey.config.ts`. Keep `work/evidence/e2/live-ledger/` across any test fix and retry. The test expects an existing account and no confirmed E2 brand doc before the interview.
5. Run the `keep-after-tests` gate. Compare the Instagram handle and the AI permission with the previous Keep results.

If runner environment variables change, stop the old agent-device daemon before the next run. Leave any live phone claim with its owner. The sample suite uses an isolated fixture library and sample data for B4 and B5. The four Instagram permission cases use launch overrides and leave saved decisions alone. The older real consent-choice test is skipped on the personal bundle.
