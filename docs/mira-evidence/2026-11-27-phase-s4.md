# Phase S4 — Mira server job state machine

Branch: `claude/mira-s4-server-jobs`. Base: `725c646`. The [failure modes](2026-11-27-phase-s4-failure-modes.md) and baseline transition inventory were committed before implementation.

## Database transitions

| Stored status | Allowed next status | Conditions |
| --- | --- | --- |
| `queued` | `running` | The retry time has arrived, fewer than three attempts were made, and the claim adds one attempt and a new lease. |
| `queued` | `failed`, `cancelled` | SQL expires stale queued work, or the cancel endpoint stops it. |
| `running` | `running` | The old lease has expired. The claim meets the same retry-time, attempt, and new-lease rules. |
| `running` | `queued` | A transient failure can retry with fewer than three attempts. The worker sets a backoff of five seconds per attempt. |
| `running` | `succeeded`, `failed`, `cancelled` | The worker saves a result or failure, SQL expires stale or exhausted work, or the cancel endpoint stops the job. |
| `succeeded`, `failed`, `cancelled` | None | A terminal row stays fixed. |

The trigger rejects other updates with `mira_invalid_job_transition` (SQLSTATE `23514`). A non-claim transition preserves the attempt count and lease columns. The worker still matches its lease ID when saving output or an error.

`20261127190000_mira_job_state_machine.sql` adds the parameterized RPC, replaces the legacy RPC body, and creates the trigger last. The trigger applies to future updates. The migration adds no column or index and scans no existing rows. The trigger needs a brief table DDL lock. The migration uses replaceable objects for a safe re-run.

## API phase

| Row at response time | `phase` | Existing `state` |
| --- | --- | --- |
| Queued with no attempts | `queued` | `working` |
| Queued after an attempt | `waiting_to_retry` | `working` |
| Running with an expired lease and fewer than three attempts | `waiting_to_retry` | `working` |
| Other running row | `running` | `working` |
| Terminal row | `succeeded`, `failed` or `cancelled` | Same value |

An expired third attempt remains `running` in the response snapshot until the claim RPC records `failed`. A response can report the state read before the worker completes. `phase` is computed from that same row and is an extra key on the existing job object. The response keeps `id`, `inputRevision`, `input`, `state`, `output` and `error` with their existing meanings. The app uses `JSONDecoder` for a response containing the synthesized `Codable` `MiraJob`. That decoder reads the declared keys and ignores `phase`.

## Lease policy

- Before S4, the RPC granted 90 seconds. The adapters set separate 55-second timeouts.
- S4 keeps a 55-second provider timeout for every current operation and a 90-second SQL floor. The one-argument `mira_claim(uuid)` still grants 90 seconds. The new overload returns `mira_lease_too_short` (SQLSTATE `22023`) for a requested lease under 90 seconds or a null duration.
- The worker requests `max(90 s, ceil((timeout + 20 s + 5 s) / 1 s))` seconds. The 20-second margin gives the worker time to finish processing and save the result, with room for scheduling, network and clock differences. The additional five seconds allow for the claim response and local preparation before the budget check. Current calls request 90 seconds and need at least 75 seconds remaining at the check.
- The worker checks the returned expiry before creating the provider abort signal. An insufficient or invalid expiry fails with `mira_insufficient_lease_budget` in the job error and the worker log. The worker makes no provider call on that path.
- For D2, add a timeout for each new operation to the exhaustive policy in `job-policy.ts`. The lease grows from that timeout. Pass the same signal to the full request and body read. The policy covers upcoming long calls without a heartbeat. D2 still needs runtime validation of its provider and Edge time limits.

### Undo SQL

If an undo is approved, restore the preceding Edge function revision first. Its one-argument claim works with either schema. Then apply this SQL as one transaction. Record the rollback in migration history through the approved release process before a reapply.

```sql
begin;

drop trigger if exists mira_job_transition on public.mira_generation_jobs;
drop function if exists public.mira_enforce_job_transition();

create or replace function public.mira_claim(p_id uuid)
returns setof public.mira_generation_jobs language plpgsql security definer set search_path = public as $$
begin
  update public.mira_generation_jobs set status='failed', error='worker_interrupted_retry_limit', updated_at=now()
    where id=p_id and status='running' and lease_until<now() and attempts>=3;
  return query update public.mira_generation_jobs
    set status='running', attempts=attempts+1, lease_id=gen_random_uuid(), lease_until=now()+interval '90 seconds', updated_at=now()
    where id=p_id and attempts<3 and next_attempt_at<=now()
      and (status='queued' or (status='running' and lease_until<now())) returning *;
end $$;

drop function if exists public.mira_claim(uuid, integer);
commit;
```

## Limits and documentation differences

- S4 was verified locally. Hosted migration, hosted Edge deployment, actual provider abort behavior, and native app decoding at runtime remain unverified.
- The S1 evidence associates S4 with a late start that arrives after a missing-row cancellation. The server still returns `not_found` on that cancel. This scope guards updates to an existing job.
- The README documents `supabase stop --no-backup`. CLI 2.121.0 says that flag deletes local data volumes. S4 uses `supabase stop` to keep the volume.
- The public tracker recorded S4 as Working under `MIRA-031` at `2026-11-27T18:28:34.325Z`. The branch remained local at handoff, so the tracker record has no commit links.
